# Release v0.3.0 — Requirement Intelligence Engine

**Phase**: 3 of 7 (see project roadmap)
**Status**: Complete

## What's included

- **Text classification** (FR2): a Logistic Regression model predicting
  a requirement's Category from its Description text.
- **Statistically sound evaluation** (FR3): stratified 5-fold
  cross-validation rather than a single train/test split, appropriate
  for a ~200-example dataset.
- **Mandatory baseline comparison** (FR4): every training run reports a
  `DummyClassifier` (majority-class) baseline alongside the real
  model's metrics — never trust an accuracy number in isolation.
- **Model persistence** (FR5/FR6): the final model and its run metadata
  (hyperparameters, metrics, dataset size, timestamp) are saved
  together for reproducibility.
- **Data quality validation** (FR9): the pipeline fails fast and
  explicitly if any class has too few examples, rather than training
  silently on insufficient data.
- **Extensible classifier factory** (FR8): adding Decision Tree, Random
  Forest, or SVM support later requires one new registry entry, not a
  pipeline rewrite.

## Real results

| Metric | Model | Baseline |
|---|---|---|
| Accuracy | **83.5%** | 17.5% |
| Precision (macro) | 86.5% | 2.2% |
| Recall (macro) | 81.9% | 12.5% |
| F1 (macro) | 82.4% | 3.7% |

(Mean across 5 stratified cross-validation folds, on 200 real generated
requirements across 8 categories.)

The model also correctly classified a hand-written, previously unseen
requirement description as "Security" — evidence of genuine
generalization, not memorization of training examples.

## The most important decision in this release didn't touch any code

Before writing a single line of the classifier, the original random
label-assignment design from Feature 0001 was identified as producing
**zero learnable signal** between requirement text and its Category —
any model trained on it would perform identically to random guessing,
regardless of algorithm choice or tuning. This was caught by questioning
whether the target variable was predictable *before* training anything,
not by debugging poor results afterward.

The fix ([ADR-0004](https://github.com/funk1090/ai-solution-architect-portfolio/blob/main/docs/architecture/adr/0004-correlated-synthetic-labels.md))
injected category-specific vocabulary into the synthetic data generator,
with 15% controlled noise to keep the problem learnable but non-trivial.
The 83.5%-vs-17.5% result above is the direct payoff of that decision.

## Architecture highlights

- Third application of the Strategy/Factory pattern in this codebase
  (after document generators and document parsers) — proof the pattern
  scales across genuinely different domains (content generation, file
  parsing, ML model selection) without modification.
- Independent uv project (`backend/requirement_classifier/`), following
  the same module-isolation strategy as Phase 2.

## Known technical debt (tracked, not hidden)

- The `document_metadata`/`ingested_content` table schemas are now
  duplicated across three independent modules. Extracting a shared
  internal package is the top-priority architecture task for the next
  session (see [ADR-0003](https://github.com/funk1090/ai-solution-architect-portfolio/blob/main/docs/architecture/adr/0003-module-structure-phase-2.md)).
- The `uv` workspace auto-discovery issue that affected Phase 2 recurred
  once more during this phase's setup — now documented as a standing
  procedure to prevent a third occurrence.
