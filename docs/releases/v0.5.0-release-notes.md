# Release v0.5.0 — Performance Lab

**Phase**: 5 of 7 (see project roadmap)
**Status**: Complete

## What's included

- **Batched embedding generation** (FR3): the indexing pipeline now
  calls the embedding model once per document, covering every pending
  chunk, instead of once per chunk.
- **Parallel document parsing** (FR4): the ingestion pipeline can
  distribute parsing across CPU cores via `multiprocessing.Pool`
  (`uv run ingestion-pipeline ingest --parallel`).
- **Reusable benchmark commands**: `knowledge-assistant
  benchmark-embeddings` and `ingestion-pipeline benchmark` measure
  real, reproducible before/after timings — no theoretical estimates.
- **Design improvement**: `_process_single_document` extracted as a
  pure, database-free function shared by both the sequential and
  parallel ingestion code paths — one place where parsing/error-handling
  logic is defined, fully unit-testable without a live database or real
  multiprocessing.

## Real, measured results

| Optimization | Before | After | Speedup |
|---|---|---|---|
| Embedding batching | 0.642s (25 chunks, one call each) | 0.042s (1 batched call) | **15.3x** |
| Parallel ingestion | 3.31s (200 documents, sequential) | 0.52s (240 documents, parallel) | **~6.4x** |

Both numbers come from this project's own hardware, following this
phase's own rule: measured, not assumed (NFR4).

## A second real bug, and an unplanned validation

The first implementation of the parallel ingestion path created a new
database engine **per document** instead of once per worker process.
On a 240-document run, this opened more simultaneous PostgreSQL
connections than the default `max_connections` allows, failing with
`FATAL: sorry, too many clients already`. Fixed by moving engine
creation into `multiprocessing.Pool`'s `initializer`, so exactly
`worker_count` engines exist for the entire run.

The failed run had already saved a subset of documents before crashing.
Retrying the fixed code correctly skipped every already-saved document
and only processed the rest — an unplanned, real-world confirmation
that Feature 0002's idempotency guarantee holds even when a run fails
partway through, not just in unit tests.

## Architecture highlights

- Both fixes were validated against genuinely identified bottlenecks
  (profiled and confirmed before writing any code), not assumed
  inefficiencies — directly following the source material's own
  "measure before optimizing" discipline (High Performance Python,
  CS:APP).
- No new independent uv project introduced: benchmarking was added
  directly to the two existing modules whose pipelines were being
  optimized, avoiding indirection for its own sake.
- All 31 existing unit tests across 4 modules pass unchanged (NFR3: no
  regressions from introducing parallelism or batching).
